# راه‌اندازی سیستم اعلان RepairDesk

این سیستم از الگوی Outbox استفاده می‌کند: ساخت یا تغییر وضعیت سفارش فقط یک رکورد اعلان را داخل همان تراکنش دیتابیس می‌سازد و ارسال واقعی را worker انجام می‌دهد. بنابراین قطع بودن پنل پیامکی باعث از بین رفتن سفارش یا اعلان نمی‌شود.

## حالت توسعه بدون پنل پیامکی

این پروژه عمداً فایل `.env` را خودکار بارگذاری نمی‌کند؛ `.env.example` فقط فهرست نمونه‌ی متغیرهاست. متغیرها باید در محیط همان process که Django یا worker را اجرا می‌کند تعریف شوند. برای نمونه در PowerShell فعلی:

```powershell
$env:NOTIFICATION_PROVIDER = 'fake'
$env:NOTIFICATION_SEND_MODE = 'auto'
$env:PUBLIC_TRACKING_BASE_URL = 'http://localhost:5173/track'
```

این مقادیر فقط تا بسته‌شدن همان پنجره باقی می‌مانند. در سرور باید آن‌ها را در تنظیمات سرویس، container، CI/CD یا حساب کاربری اجرای Task Scheduler تعریف کنید؛ صرفاً کپی‌کردن `.env.example` به `.env` اثری ندارد.

متغیرها را روی مقادیر زیر نگه دارید:

```env
NOTIFICATION_PROVIDER=fake
NOTIFICATION_SEND_MODE=auto
PUBLIC_TRACKING_BASE_URL=http://localhost:5173/track
```

Fake provider هیچ درخواست اینترنتی نمی‌فرستد و اعلان را با وضعیت `simulated` ثبت می‌کند. این حالت برای توسعه و نمایش کامل رابط کاربری مناسب است.

## انتخاب شمارهٔ گیرنده

اگر `available_phone_number` پر باشد، فقط همان شمارهٔ در دسترس گیرندهٔ پیامک است. اگر خالی باشد، `phone_number` اصلی استفاده می‌شود. یکسان‌بودن دو شماره مجاز است و باعث ارسال دو پیامک نمی‌شود.

گیرنده هنگام ساخت اعلان ثبت می‌شود و درست پیش از اولین تلاش، از اطلاعات فعلی مشتری دوباره انتخاب می‌شود؛ به این ترتیب اعلان‌های قبلیِ هنوز ارسال‌نشده هم از شمارهٔ در دسترس استفاده می‌کنند. بعد از اولین تلاش، گیرنده برای retry ثابت می‌ماند تا یک پیام ناخواسته به دو شماره ارسال نشود. شمارهٔ دومِ نامعتبر به‌صورت خاموش با شمارهٔ اصلی جایگزین نمی‌شود و خطای تنظیمات می‌گیرد.

## راه‌اندازی SMS.ir

ابتدا در پنل SMS.ir برای سه رویداد «ثبت سفارش»، «انتظار برای قطعه» و «آماده تحویل» قالب جدا بسازید. لغو سفارش در برنامه و تاریخچه ثبت می‌شود، اما پیامک ندارد و قالبی برای آن لازم نیست. پیامک‌های لغو قدیمی که هنوز در صف باشند نیز هنگام پردازش بدون ارسال متوقف می‌شوند؛ سوابق ارسال‌شده حفظ می‌شوند. نام پارامترهای قالب‌ها باید با `NAME`، `CODE` و `LINK` هماهنگ باشد. سپس این متغیرها را در محیط سرور تعریف کنید؛ فایل `.env` واقعی را commit نکنید:

برای تأیید قالب در SMS.ir، دامنهٔ سایت را در متن ثابت بنویسید و فقط انتهای لینک
را متغیر بگذارید. نمونه برای دامنهٔ این استقرار:

```text
#NAME# گرامی،
سفارش تعمیر دستگاه شما با کد #CODE# ثبت شد.
پیگیری سفارش: https://suncitymobile.ir/#LINK#
```

در هر سه قالب، پیشوند ثابت `https://suncitymobile.ir/` باید با دامنهٔ
`PUBLIC_TRACKING_BASE_URL` یکسان باشد. adapter مربوط به SMS.ir مقدار `LINK` را به
شکل `track?code=RD...` می‌فرستد؛ مقدار URL کامل همچنان در context اعلان ذخیره می‌شود.
طبق محدودیت نمایش‌داده‌شده در پنل، مقدار هر پارامتر حداکثر ۴۰ کاراکتر است؛ طول بیشتر
پیش از درخواست شبکه با خطای تنظیمات متوقف می‌شود. متن قالب‌های قبلی که فقط `#LINK#`
داشتند را هم‌زمان با انتشار این نسخه اصلاح و دوباره برای تأیید ارسال کنید.

```env
NOTIFICATION_PROVIDER=smsir
NOTIFICATION_SEND_MODE=auto
PUBLIC_TRACKING_BASE_URL=https://example.com/track
SMSIR_API_KEY=replace-with-real-secret
SMSIR_TEMPLATE_REPAIR_CREATED=100001
SMSIR_TEMPLATE_REPAIR_WAITING_FOR_PARTS=100002
SMSIR_TEMPLATE_REPAIR_READY=100003
```

قبل از اجرا تنظیمات را بررسی کنید:

```powershell
.\.venv\Scripts\python.exe manage.py check
```

سپس migrationهای دیتابیس را اعمال کنید:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
```

کلید API فقط باید در متغیر محیطی سرور قرار بگیرد. آن را در Git، لاگ یا پاسخ API ذخیره نکنید. پس از افشای احتمالی نیز کلید را از پنل باطل و جایگزین کنید.

## راه‌اندازی کاوه‌نگار

در پنل کاوه‌نگار سه قالب خدماتی Lookup برای ثبت سفارش، انتظار برای قطعه و آماده تحویل بسازید. نام قالب باید انگلیسی و بدون فاصله یا `_` باشد. در متن هر قالب `%token` کد رهگیری و `%token10` نام مشتری است. لینک ثابت سایت را داخل خود قالب بنویسید؛ برای نمونه:

```text
%token10 عزیز، سفارش شما آماده تحویل است.
پیگیری: https://example.com/track?code=%token
```

سپس تنظیمات محیطی را تعریف کنید:

```env
NOTIFICATION_PROVIDER=kavenegar
NOTIFICATION_SEND_MODE=auto
PUBLIC_TRACKING_BASE_URL=https://example.com/track
KAVENEGAR_API_KEY=replace-with-real-secret
KAVENEGAR_TEMPLATE_REPAIR_CREATED=RepairCreated
KAVENEGAR_TEMPLATE_REPAIR_WAITING_FOR_PARTS=RepairWaiting
KAVENEGAR_TEMPLATE_REPAIR_READY=RepairReady
```

این adapter از API رسمی `verify/lookup.json` استفاده می‌کند و بنابراین سرویس پیشرفته و تأیید قالب‌ها در پنل لازم است.

## اجرای worker

برای اجرای وب و Worker در همان سرویس فعلی و استفاده از همان Secretها،
[راهنمای اجرای مشترک](deployment-combined-web-worker.md) را دنبال کنید.
این حالت با `RUN_SMS_WORKER=true` و `NOTIFICATION_SEND_MODE=worker` فعال می‌شود.

در اجرای مشترک لینوکسی، بعد از commit یک علامت محلی سبک از وب به Worker فرستاده می‌شود تا برای نوبت بعدی صبر نکند. این علامت دادهٔ پیامک ندارد و صف اصلی همچنان در دیتابیس است. در صورت نرسیدن علامت یا اجرای Worker در کانتینر جدا، بررسی دوره‌ای با فاصلهٔ ۵ ثانیه مسیر پشتیبان است. هر نوبت حداکثر ۱۰۰ رکورد را به‌ترتیب بررسی می‌کند؛ مدت پردازش نوبت و زمان پاسخ SMS.ir/اپراتور به این فاصله اضافه می‌شوند.

اتصال سالم دیتابیس بین نوبت‌ها دوباره استفاده می‌شود و اتصال‌های قدیمی/خراب کنار گذاشته می‌شوند. علامت محلی غیرفعال یا صف سوکت پر، ثبت سفارش را خراب نمی‌کند. برای اجرای پیوسته:

```sh
python manage.py run_notification_worker --interval 5 --limit 100
```

فرمان زیر حداکثر ۱۰۰ اعلان آماده را پردازش می‌کند و سپس خارج می‌شود:

```powershell
.\.venv\Scripts\python.exe manage.py process_notifications --limit 100
```

در ویندوز این فرمان را با Task Scheduler هر یک دقیقه اجرا کنید. گزینه «اجرای نمونه جدید هنگام فعال بودن نمونه قبلی» را روی جلوگیری از اجرای هم‌زمان بگذارید. در لینوکس می‌توان همین فرمان را هر دقیقه با cron یا timer سرویس اجرا کرد. خود پردازشگر نیز claim اتمیک، بازیابی رکوردهای گیرکرده و محافظ attempt دارد.

برای provider واقعی از `auto` یا `worker` استفاده کنید تا درخواست HTTP کاربر منتظر پنل پیامکی نماند. حالت `sync` فقط برای عیب‌یابی محلی است.

## retry و بازیابی

مقادیر پیش‌فرض چهار تلاش با فاصله‌های ۶۰، ۳۰۰ و ۹۰۰ ثانیه است. خطاهایی که معلوم است درخواست ارسال نشده یا رد شده، مانند شکست DNS، اتصال ردشده و پاسخ 429، دوباره تلاش می‌شوند. کلید یا قالب نامعتبر تا اصلاح تنظیمات و retry دستی متوقف می‌ماند.

Timeout، قطع اتصال پس از شروع درخواست، پاسخ ناقص/نامعتبر، HTTP 408/5xx و رکورد `processing` منقضی‌شده برای provider واقعی، ممکن است مربوط به پیامکی باشند که پنل قبلاً پذیرفته است. این موارد با `status=failed`، `error_code=delivery_unknown` و `is_retryable=false` نگه داشته می‌شوند و خودکار دوباره ارسال نمی‌شوند. ابتدا گزارش پنل پیامکی را بررسی کنید. در صفحهٔ اعلان‌ها این موارد «نیاز به بررسی ارسال» نمایش داده می‌شوند و retry نیازمند تأیید خطر ارسال تکراری است. API نیز برای این موارد `confirm_unknown_delivery: true` می‌خواهد؛ بدون آن 409 برمی‌گرداند.

این راهکار تضمین سراسری «دقیقاً یک ارسال» نیست: پنل خارجی و دیتابیس پروژه تراکنش مشترک ندارند و adapterها کلید idempotency را به پنل نمی‌فرستند. در نتیجهٔ نامشخص، اولویت با جلوگیری از ارسال دوبارهٔ خودکار است و ممکن است بررسی انسانی لازم شود. رسیدن پاسخ موفق دیرهنگام همان تلاش، در صورت شروع‌نشدن تلاش جدید، نتیجه را اصلاح می‌کند.

پیامک‌های وضعیتِ منسوخ، سفارش لغوشده یا حذف‌شده بدون ارسال کنار گذاشته می‌شوند. در برگشت چندبارهٔ سفارش به یک وضعیت، فقط پیامک آخرین تغییر وضعیت معتبر است. این بررسی هنگام claim انجام می‌شود؛ تغییر وضعیت سفارش پس از شروع درخواست شبکه قابل پس‌گرفتن نیست.

با SIGTERM، Worker پیامک در حال ارسال را تمام می‌کند و پیامک بعدی را شروع نمی‌کند. زمان مهلت توقف کانتینر باید از زمان معمول درخواست پیامکی بیشتر باشد. برای Worker پورت HTTP تعریف نکنید. بعد از تغییر کد مشترک اعلان‌ها، هم Django و هم Worker را به‌روز کنید.

برای تولید بستهٔ آمادهٔ آپلود، بدون فایل‌های محیطی، دیتابیس، اسکرین‌شات و مدارک محلی:

```powershell
.\.venv\Scripts\python.exe deploy/package_worker.py --output artifacts/repairdesk-worker-reviewed.zip
```

```env
NOTIFICATION_PROCESSING_TIMEOUT_SECONDS=300
NOTIFICATION_MAX_ATTEMPTS=4
NOTIFICATION_RETRY_DELAYS_SECONDS=60,300,900
```

صفحه اعلان‌های داشبورد برای مدیر و پذیرش، وضعیت صف و خطا را نشان می‌دهد و retry دستی را فراهم می‌کند.
