# بازبینی صف پیامک و Worker — ۲۰۲۶-۱۱-۲۲

## نتیجه و محدوده

مسیر ساخت اعلان، claim اتمیک، ارسال HTTP، ثبت نتیجه، retry، توقف Worker و صفحهٔ اعلان‌ها بررسی شد. برای این تغییرات migration جدید لازم نیست. تغییرات هنوز commit یا روی سرور منتشر نشده‌اند.

## ایرادهای اصلاح‌شده

- **ارسال دوباره پس از پاسخ نامشخص:** timeout، قطع ارتباط بعد از شروع ارسال، پاسخ JSON ناقص/نامعتبر، پاسخ 408/5xx و پاسخ موفق بدون شناسهٔ معتبر، دیگر باعث resend خودکار نمی‌شوند. این موارد `delivery_unknown` و نیازمند بررسی گزارش پنل هستند. شکست DNS، اتصال ردشده و رد صریح موقت مانند 429 همچنان طبق backoff تکرار می‌شوند.
- **بازیابی claim واقعی پس از توقف ناگهانی:** Worker دوم رکورد واقعیِ `processing` منقضی‌شده را خودکار دوباره نمی‌فرستد. رکورد fake به دلیل نداشتن ارسال واقعی همچنان قابل بازیابی خودکار است.
- **پاسخ موفق دیرهنگام:** پاسخ همان تلاش، با کنترل شمارهٔ تلاش، می‌تواند نتیجهٔ نامشخص را به ارسال موفق تبدیل کند؛ نتیجهٔ تلاش قدیمی اجازهٔ بازنویسی تلاش جدیدتر ندارد.
- **خطای دیتابیس بعد از پذیرش پنل:** ثبت نتیجه خارج از catch خطاهای provider انجام می‌شود؛ خطای ذخیرهٔ نتیجه به‌اشتباه به خطای قابل‌تکرار ارسال تبدیل نمی‌شود.
- **پیامک منسوخ:** سفارش حذف/لغوشده و پیامک مربوط به وضعیت قدیمی ارسال نمی‌شود. در برگشت چندباره به انتظار قطعه، فقط اعلان مربوط به آخرین تغییر وضعیت معتبر است.
- **توقف بین پیامک‌ها:** SIGTERM به پردازشگر صف منتقل می‌شود؛ پس از تمام‌شدن پیامک جاری، رکورد بعدی شروع نمی‌شود. شمارندهٔ `deferred` باقی‌ماندهٔ نوبت را در لاگ نشان می‌دهد.
- **ورودی نامعتبر Worker:** مقدار صفر، منفی، NaN و Infinity برای فاصلهٔ اجرا رد می‌شود.
- **ارسال دستی مبهم:** در رابط کاربری هشدار و تأیید لازم است. API نیز تأیید صریح `confirm_unknown_delivery: true` می‌خواهد و درخواست ناقص/نامعتبر را رد می‌کند.

## اعتبارسنجی انجام‌شده

- کل تست‌های بک‌اند پس از اضافه‌شدن اجرای مشترک: **۱۰۲ تست موفق** روی SQLite موقت.
- تست‌های رابط کاربری: **۲۳ تست موفق**؛ شامل انصراف از ارسال دستیِ نامشخص و ارسال تأیید صریح به API.
- `pnpm lint` و build/typecheck نسخهٔ production: موفق.
- بررسی migration: `No changes detected`.
- بستهٔ Worker باز شد، فایل‌های آن با منبع مقایسه شدند، کدهای Python parse شدند و `manage.py check` با تنظیمات production آزمایشی و `run_notification_worker --help` از داخل بسته اجرا شدند؛ موفق.
- تمام فایل‌های بستهٔ وب با خروجی build مقایسه شدند؛ فایل index آخر بسته است. هیچ فایل محیطی، کلید، دیتابیس یا خروجی مرورگر داخل بسته‌ها قرار نگرفته است.
- تست‌های خرابی با provider شبیه‌سازی‌شده انجام شدند؛ هیچ پیامک واقعی یا تغییر در دیتابیس اصلی انجام نشد.

## محدودیت‌های واقعی

تراکنش مشترک بین MySQL پروژه و پنل خارجی وجود ندارد و adapterها کلید idempotency را به پنل نمی‌فرستند. بنابراین تضمین سراسری «دقیقاً یک ارسال» ارائه نمی‌شود. در نتیجهٔ نامشخص، جلوگیری از resend خودکار بر تکرار احتمالی پیام اولویت دارد؛ بررسی دستی گزارش پنل ممکن است لازم شود.

قفل و شمارهٔ تلاش در کد و با سناریوهای اجرای درهم‌تنیده تست شدند؛ اجرای هم‌زمان واقعی روی MySQL production اینجا تست نشده است. Docker Engine محلی در دسترس نبود، بنابراین build/run ایمیج Docker انجام نشد. اجرای مشترک Gunicorn/Supervisor روی Ubuntu موجود، با بارکاری ایزوله و بدون دیتابیس یا SMS واقعی، تست شد: یک Worker در کنار سه پردازش وب، restart پس از crash، توقف هماهنگ و توقف مدیر در شکست دائمی شروع موفق بودند. برای Worker مستقل سلامت‌سنجی HTTP مناسب نیست؛ سرویس مشترک وب/Worker همچنان پورت HTTP وب را دارد.

ارسال شبکه‌ای شروع‌شده قابل پس‌گرفتن نیست. بررسی منسوخ‌بودن اعلان هنگام claim انجام می‌شود؛ تغییر وضعیت سفارش بعد از آن ممکن است با پیامک در حال ارسال هم‌زمان شود. ارسال‌ها ترتیبی‌اند؛ فاصلهٔ ۶۰ ثانیه بعد از پایان هر batch محاسبه می‌شود، نه یک تضمینِ تأخیر حداکثر ۶۰ ثانیه برای هر پیام.

## انتشار

مسیر انتخاب‌شدهٔ فعلی، اجرای Worker در همان سرویس Django است؛
[راهنمای اجرای مشترک](deployment-combined-web-worker.md) را دنبال کنید.
بستهٔ ZIP زیر برای روش اختیاری Worker مستقل است.

۱. تغییرات مشترک را برای Django و Worker منتشر کنید؛ صفحهٔ اعلان‌های فرانت‌اند نیز باید به‌روز شود.
۲. Worker را از بستهٔ `artifacts/repairdesk-worker-2026-11-22-reviewed.zip` بسازید. این بسته جایگزین بستهٔ اولیهٔ همان روز است.
۳. بستهٔ فرانت‌اند: `artifacts/repairdesk-web-2026-11-22-worker-review.tar.gz`.
۴. قبل از فعال‌کردن Worker، صف اعلان‌های واقعیِ قدیمی را بررسی کنید؛ شروع Worker رکوردهای معتبرِ آماده را پردازش می‌کند.
۵. استقرار، اتصال MySQL، تنظیمات Probe و سپس ارسال/دریافت واقعی را با شمارهٔ متعلق به خودتان بررسی کنید.

برای بازتولید بستهٔ Worker:

```powershell
.\.venv\Scripts\python.exe deploy/package_worker.py --output artifacts/repairdesk-worker-2026-11-22-reviewed.zip
```
